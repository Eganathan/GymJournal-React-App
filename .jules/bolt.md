## 2025-03-09 - Metrics Logging Sequential Updates Bottleneck
**Learning:** Sequential `await` calls in a `for` loop (like `updateEntry` when saving many metrics in `MetricsLog`) can severely degrade client performance by chaining I/O latency. O(n) waiting time limits UI responsiveness during saves. However, merely parallelizing with `Promise.all` can crash the UI or spam the backend if the underlying store functions implicitly trigger independent heavy state refresh calls (like `fetchSnapshot()`) after each successful atomic update.
**Action:** When parallelizing operations that inherently fetch fresh global state on success, always introduce an options flag (e.g., `{ skipSnapshotRefresh: true }`) to bypass those side effects. Batch the operations together using `Promise.all()`, then manually orchestrate exactly one cache invalidation and state refresh after all batching promises complete.
