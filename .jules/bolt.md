## 2024-05-18 - Replacing sequential API loops with Promise.all
**Learning:** Updating multiple metrics sequentially via a loop (`for...of`) creates unnecessary latency due to consecutive network round-trips. When batch endpoints are unavailable, issuing parallel asynchronous calls speeds up the entire operation significantly. Furthermore, when underlying Zustand store actions (like `updateEntry`) automatically invalidate and refetch data (e.g. `fetchSnapshot`), parallelizing them triggers redundant parallel refresh requests which negates performance gains.
**Action:** Refactor sequential `for...of` network loops into `Promise.all`. Crucially, when parallelizing store actions that trigger side-effects like cache-refreshes, introduce and pass configuration options (e.g., `{ skipSnapshotRefresh: true }`) to bypass these inner side-effects, then execute a single manual invalidation and refetch once `Promise.all` resolves.
